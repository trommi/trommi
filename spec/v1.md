# Trommi protocol, version 1

Normative. MLS (RFC 9420) distributes every key; this file says how Trommi uses it and what clients, connector and
hub must do. Every numbered line is a MUST; "refused (`code`)" names the stable error code. A heading marked "(Dn)"
is a construct of Trommi's own where MLS has no mechanism; [`v1-deviations.md`](v1-deviations.md) says why each was
chosen. Hub routes and tables: [`hub-api.md`](hub-api.md). On the wire this version carries the number 1: the `v1.`
of a link, the `/v1/` routes, the label `trommi apns v1`, the hub's `protocol_version`. The `version` and
`schema_version` fields inside envelopes and stored state number their formats, not the protocol. A byte string
`trommi/v1/…` is a label of the account (8.9). Section numbers are stable, since code and tests cite them; 18 is not used.

## 1. The two trees

**Content: what a person or an agent has.** Sorting is not encryption: which Desk an Agent is on, the order, the
crown and which Helper hangs under which Agent are register values; moving changes no key and moves no data.

```
Room                                          everything of one account (an account has a list of rooms; one for now)
├── Desk                                      a register (name, order, crown, Goals)               room group
│   ├── Goals                                 in the Desk's register; copied into each Agent's session for the agent
│   └── Scribble Board (one per Desk,         items: stroke, text, sticky, voice note, picture,    room group
│       one for "All desks")                  move, erase, send away; snapshot = a file
│       └── piece of a stroke in progress     relayed live, never stored (an MLS message)
├── Note                                      versions; sending it makes a Chat message             room group
├── per-card markers                          Later (snooze), duck, drafts, read marks: registers   room group
├── Agent (a session)                         everything below is that one session                  its session group
│   ├── Chat                                  messages, attachments; the terminal's input and final answer
│   ├── work trail                            "Working · 3 steps": MLS messages
│   ├── Decision card, Info card              versions; answer, take back; the card's own Chat
│   ├── permission request + verdict
│   ├── Artifact                              a published Page or Media: versions, files; Share link
│   ├── Status line, agent profile, Goals     registers
│   └── Helper (a child session)              the same again, in a session group of its own
└── Push, Live Activity                       no content: how the hub reaches a device
```

**Keys: what only protects.**

```
Account (e-mail; password or passkey)         the hub checks the login; no key here
└── sealed copies of the recovery code        under the password, the Emergency Kit words, each passkey        (D1)
    └── recovery code → recovery key          public halves in the room group's context; not a member

Device                                        one Ed25519 signature key = its id; KeyPackages at the hub

Room group (MLS)                              all of the person's devices. Not a Desk.
└── content key, per epoch                    MLS exporter; protects Desks, Goals, Scribble Boards, Notes, markers

Session group (MLS), one per Agent/Helper     the person's devices + that session's agent device(s)
└── content key, per epoch                    MLS exporter; protects Chat, cards, permission requests, Artifacts,
                                              Status lines

Old content keys                              kept by every device that had them; handed to a new device or to an
                                              agent taking a session over in an MLS message; one sealed copy per
                                              group and epoch at the hub for the recovery key                  (D1)
File key                                      random, one per file; inside the encrypted body that names the file,
                                              and after the # of a Share link                                  (D3)
```

- Two boundaries only: the room (the person's devices) and each single session (those devices and its agent devices).
- The hub stores public group state, ordered group messages and ciphertext; it never holds a key or reads content.
- Not forward secret for history, by decision: whoever holds a human device's state or the recovery code reads the
  whole history. After a device's next update or its removal, a copied group state opens nothing new.

## 2. Terms

| In the app | In the protocol |
| --- | --- |
| (never named) | **room**: one room group, its session groups, its stored content. `room_id`: 32 random bytes |
| your devices | **human devices**: the leaves of the room group |
| Agent | a **main session** (`session_id`: 16 random bytes) with one **agent device** (a connector installation) |
| Helper | a **helper session**: a session whose `parent` names a main session |
| Chat, Scribble Board | a **timeline** of items (`session/<id>`, `card/<id>`, `desk/<id>`) |
| Decision card, Info card, Note, permission request, Artifact | an **object** with versions; types card, note, request, artifact |
| Desk, Goals, Status line, profile, markers | **registers**: named values, the newest counts |
| (not shown) | **group**: an MLS group. **epoch**: its key period. **envelope**: one stored, signed, encrypted item (section 9) |

Encoding: TLS presentation language as in RFC 9420 section 2 (variable-length vectors `<V>`), produced by the
`tls_codec` crate. `SignWithLabel`, `EncryptWithLabel`, `RefHash`, `ExpandWithLabel`, `MLS-Exporter` are the functions
of RFC 9420 sections 5.1.2, 5.1.3, 5.2 and 8; labels are given without the prefix those functions add. Times are
`uint64` milliseconds since the Unix epoch. In JSON and links, bytes are base64url without padding. A Commit, Welcome,
GroupInfo, KeyPackage or application message always travels, is stored and is hashed as the TLS-encoded `MLSMessage`
that OpenMLS emits (`MlsMessageOut::tls_serialize_detached`); only the reference by which a Welcome names its
receiver is RFC 9420's `KeyPackageRef`, over the KeyPackage itself.

## 3. MLS profile

| | |
| --- | --- |
| Library | OpenMLS `=0.9.1`, `openmls_rust_crypto =0.6.0`, `openmls_basic_credential =0.6.0`, in one crate `trommi-core` used by web (WASM), iOS (UniFFI), connector and hub. No second implementation |
| Version, suite | `mls10`; `MLS_128_DHKEMX25519_CHACHA20POLY1305_SHA256_Ed25519` (0x0003). No negotiation |
| Credential | `BasicCredential`; `identity` = the 32-byte Ed25519 public key, equal to the leaf's `signature_key`. This key is the **device id** |
| Capabilities of every leaf and KeyPackage | versions `[mls10]`, suites `[0x0003]`, credentials `[basic]`, extensions `[0xF001, 0xF002, last_resort]`, proposals: default |
| Group context | `required_capabilities` naming extensions 0xF001 and 0xF002; plus `trommi_room` (0xF001) in a room group or `trommi_session` (0xF002) in a session group |
| Handshake | `PublicMessage` (`PURE_PLAINTEXT_WIRE_FORMAT_POLICY`): the hub and observers follow every group |
| Proposals | only inside a Commit, by value: Add, Remove, GroupContextExtensions (room group only), ExternalInit. Standalone proposals, Update proposals, PreSharedKey, ReInit and external proposals are refused (`bad-commit`) |
| Welcome, GroupInfo | every Welcome and every GroupInfo carries the `ratchet_tree` extension; GroupInfo also `external_pub` |
| Application messages | `PrivateMessage`, for the four message types of section 7 only |
| Lifetimes | every KeyPackage and every founder's leaf (`MlsGroupCreateConfig::builder().lifetime(..)`): from one hour ago to ten years ahead, the application's maximum; a KeyPackage that claims more is refused. Freshness is the hub's, which hands out no KeyPackage uploaded more than 90 days ago. Joins use `skip_lifetime_validation()` |
| KeyPackages | every device always has exactly one with `last_resort` at the hub, replaced every 30 days (the old one's private part is kept 30 days more), and tops up to 100 single-use ones whenever it is online; a KeyPackage taken from outside is at most 4 096 bytes |
| Past epochs | `max_past_epochs` 0: a device processes a group's log strictly in order, so every message is opened in its own epoch |

- 3.1 A device verifies with `trommi-core` alone; signature and encoding strictness are whatever the pinned crates do,
  the same code everywhere.
- 3.2 A group's `group_id` is `room_id` (32 bytes) for the room group and `room_id ‖ session_id` (48 bytes) for a
  session group.

```
struct { opaque recovery_signature_key<V>; opaque recovery_hpke_key<V>;   // section 8
         opaque agents<V>; } TrommiRoom;      // 0xF001: enrolled agent devices, 32 bytes each, ascending, no duplicates
struct { opaque room_id[32]; opaque session_id[16];
         opaque parent[16]; } TrommiSession;  // 0xF002: parent = 16 zero bytes for a main session; never changes

struct { opaque device[32]; uint64 seq; opaque hash[32]; } Cut;            // the device's last accepted envelope (9.0.10)
struct { uint8 version = 2; uint64 room_epoch; opaque room_state[32]; uint64 time;
         Cut cuts<V>; uint8 join; } CommitNote;                            // the authenticated_data of every Commit
```

- 3.3 Every Commit's `authenticated_data` is one `CommitNote`, at most 72 712 bytes (the fixed fields and one Cut
  for each leaf a group can hold). `room_epoch`: in the room group the epoch the Commit builds on; in a session
  group the room epoch whose state the committer applied. `time`: the committer's clock. `room_state`:
  `RefHash("Trommi Room State", GroupContext)` of the room group at `room_epoch`. `cuts`: one per device the Commit
  removes from the group, ascending by device, else empty. `join`: 1 in a join from outside (8.4), else 0.

| --- | --- |
| create a group | `MlsGroupCreateConfig::builder()` (`.ciphersuite`, `.wire_format_policy`, `.capabilities`, `.with_group_context_extensions` with `Extension::Unknown(type, UnknownExtension(bytes))` and `RequiredCapabilitiesExtension`, `.use_ratchet_tree_extension(true)`, `.sender_ratchet_configuration`), then `MlsGroup::new_with_group_id` |
| commit | `group.set_aad(note)` (reset after each message: set it every time), `group.commit_builder().consume_proposal_store(false)` with `propose_adds`, `propose_removals`, `propose_group_context_extensions` (replaces the whole list: keep `required_capabilities`), `load_psks`, `build`, `stage_commit`. The next epoch's key before the hub answers: `group.pending_commit()` → `StagedCommit::export_secret`. Accepted: `merge_pending_commit`; `epoch-taken`: `clear_pending_commit` |
| receive | `group.process_message` → `ProcessedMessageContent::StagedCommitMessage`: check sender, aad and proposals against section 5, then `merge_staged_commit`; `ApplicationMessage`: section 7 |
| join | `StagedWelcome::new_from_welcome` → `into_group`. From outside: `MlsGroup::external_commit_builder().with_aad(note).with_config(..).with_ratchet_tree(..).build_group(..)`, `leaf_node_parameters` with the capabilities of this section, `load_psks`, `build`, `finalize`; the group then stands in the new epoch, nothing is pending |
| keys | `group.export_secret(crypto, "trommi content", &[], 32)`: the current epoch only |
| GroupInfo | `group.export_group_info(crypto, signer, true)` |
| observe (hub; non-human devices on the room group; helper devices also on their main session's group) | `PublicGroup::from_external`, `process_message`, `merge_commit` |
| KeyPackage | `KeyPackage::builder().leaf_node_capabilities(..).key_package_lifetime(..)`, `.mark_as_last_resort()`, `.build` |
| message | `group.create_message` |
| labelled signature, hash | `ciphersuite::signable::{Signable, SignedStruct, Verifiable}`; `HashReference::new` |
| HPKE sealing | `OpenMlsCrypto::hpke_seal` / `hpke_open` with the TLS-encoded `EncryptContext` as info and empty aad (the labelled helpers are private to the crate); `derive_hpke_keypair` |

- 3.4 An external commit holds exactly one ExternalInit, at most one Remove (the joiner's own old leaf) and an update
  path; a Commit without a path holds only Adds; every other Commit has a path (RFC 9420 sections 12.2, 12.4).
- 3.5 Sender ratchets: out-of-order tolerance 50, maximum forward distance 10 000.
- 3.6 An application message opens once per device and never for its sender; whatever a device needs again it stores
  when it opens or sends it. No PSK is used anywhere.
- 3.7 A Welcome that a device refuses or cannot open uses up the single-use KeyPackage it was for. Into a session
  group a human device asks to be let in again (`POST /v1/requests`, kind `readmit`): a human device of that group
  removes its leaf, with its Cut, and adds it with a fresh KeyPackage in one Commit (9.0.10). Into the room group
  there is no second try: the leaf is removed like any removed device, and the device comes back as a new device
  with a new key (4.3). So does an agent device (13.4); a helper device: 5.3.5.

## 4. Devices and roles

- 4.1 A role is never claimed, it follows from group state. **Human device**: a leaf of the room group. **Agent
  device**: a key in `TrommiRoom.agents`. **Revoked**: a key that was once one of the two and no longer is. **Helper
  device**: a leaf of a helper session group that never was any of the three. Sets at room epoch r: `H(r)`, `A(r)`.
  A room holds at most 1000 human devices (1001 while a recovery runs, 8.7) and 256 agent devices.
- 4.2 `H` and `A` are disjoint. A revoked key is never added to the room group, to `agents` or to any session group
  again and may be a leaf of none (`bad-commit`; 5.2.8); the hub checks this against the room's whole history, a
  device against what it processed.
- 4.3 A device holds one signature key for the room, used in every group. Its private keys never leave it. A device
  that lost its state, or whose state no longer processes, is a new device with a new key: it joins like any new
  device, and its old key is removed like any removed device. Nothing is ever granted on a signature key alone.
- 4.4 Every device that is not a human device follows the room group as an observer, from the GroupInfo of the epoch
  it was told at joining (12.1.6) and every Commit after it, and so knows `H(r)`, `A(r)` and the recovery keys.
- 4.5 Before adding a device to any group, the adder checks that the KeyPackage's signature verifies, its credential
  is the intended device id and its capabilities are those of section 3; a hub cannot substitute a device.
- 4.6 **The past of a group.** A device holds a group from the epoch it joined at (a leaf) or began to follow at
  (an observer): its **first epoch**, whose GroupContext it writes down then. Of an earlier epoch it knows nothing
  until it has learned the group's past: it fetches the founding GroupInfo (epoch 0) and the Commits after it
  (`hub-api.md`: both are kept as long as any envelope of the group) and follows them as an observer, each Commit
  judged by sections 3 to 5 as every verifier judges it, up to its first epoch. The walk is taken only if the
  GroupContext it reaches there is byte for byte the one the device wrote down (`bad-group` otherwise, and nothing
  of it is kept). The confirmed transcript hash in a GroupContext chains every Commit since the founding with its
  signature, each over the GroupContext its Commit builds on (RFC 9420 section 8.2): equality at one epoch fixes
  every Commit and every state before it, and so the leaves, the roles, the notes with their room epochs, times
  and Cuts.
  - **Change numbers are the hub's word alone.** A walk needs them only to place a session Commit in the hub's
    order: against the room epoch current there, which its note must name, and for a helper session against its
    main session's agent leaf there (5.2.1; a main session can change its agent leaf within one room epoch). A
    group's Commits come under ascending numbers, and the places of the room's epochs ascend with the epochs and
    agree with those the device knows from its own log (`bad-group` otherwise; a place that the device's own log
    contradicts later is dropped, and the room epoch there is unknown again: `room-behind`). A wrong number can
    fail a walk; it cannot change a leaf, a role in the room, a note, a time or a Cut that a walk which is taken
    records. It can decide where a room epoch began in the hub's order and, where a main session had several
    agent leaves within one room epoch, which of them a helper session's Commit is judged against, and only if
    the Commit obeys section 5 against that one too. A walk does not judge the two rules about other sessions'
    liveness (5.2.2: one live main session per agent device; 5.2.5: live helper sessions per main session): no
    Commit says when a session was archived; the hub judged them when it took the Commit.
  - Order: the room group's past first (a session Commit names a room state: `room-behind`), then a main
    session's, then its helper sessions' (the opener is the main session's agent leaf at each Commit's place:
    `group-behind`).
  - The device then holds for every earlier epoch what it holds for its own (leaves, roles, the agent leaf or
    opener, the `time` of the Commit that ended it) and every Cut those Commits carry; of a key removed more than
    once, the Cut of its last removal stands for its chain (9.0.10) and its first removal for what it owned
    (9.2); with each Cut it holds the epoch that began without that leaf,
    so that a key added again goes on from its Cut in the epoch that added it (9.0.10). A leaf has in a learned
    epoch the role of 4.1 under the room state its Commit named: a revoked key that a stale group still held has
    none.
  - A device that joins with the code has walked every group before it joins (8.4, 8.5) and keeps that walk as
    its past. A device that founded a group has nothing to learn. A device may take a walk's Commits in several
    steps; nothing of a walk counts before the comparison at its end, and a walk follows at most 65 536 Commits
    of a group.

## 5. Groups

### 5.1 The room group

- 5.1.1 Founding: the first device creates the group with `TrommiRoom` and posts the GroupInfo of epoch 0.
- 5.1.2 A Commit is accepted only from a human device, with these proposals: Add of one new human device (12.1.5);
  Remove of human devices; GroupContextExtensions that changes `agents` (enrol or remove agent devices) or the
  recovery keys (8.6) and nothing else; or none (an update of the committer's own leaf).
- 5.1.3 A Commit that removes a leaf carries that device's Cut (9.0.10).
- 5.1.4 The one Commit from a non-member is the join with the code (8.4). Agent and helper devices commit nothing in
  the room group.

### 5.2 Session groups

A session group has `TrommiSession`. Let `r` be the Commit's `room_epoch`. Checks by every member and the hub:

- 5.2.1 `r` is known to the verifier (`room-behind`: process the room group first) and `room_state` is that epoch's;
  `r` is not below the `room_epoch` of the group's previous Commit, and at the hub it is the current room epoch. The
  hub also refuses a Commit being posted whose committer or added device its newest room state does not allow. A
  stored Commit is judged against the room state, and for a helper session the main session's state, at its own
  place in the hub's order (5.4.1), never against a later one.
- 5.2.2 **Main session** (`parent` zero). Committer: a human device in `H(r)` (a leaf, or joining by 8.4). After the
  Commit the leaves are human devices in `H(r)` and exactly one agent device in `A(r)` (none while the session waits
  for a takeover). An agent device is the agent leaf of at most one live main session.
- 5.2.3 **Helper session** (`parent` = P, a main session of the same room). Its **opener** is the agent device that
  is P's agent leaf now. Committer: a human device in `H(r)` (a leaf, or joining by 8.4), or the opener. After the
  Commit the leaves are human devices in `H(r)`, the opener, and at most 7 helper devices; while P has no agent
  leaf: no opener, and only human devices commit (Adds of human devices, joins by 8.4, Removes of revoked leaves).
- 5.2.4 The opener's Commits contain only: Add of devices that are not human devices, Remove of leaves that are not
  human devices, or nothing; in the founding Commit also the Adds of 5.2.5. It commits in no other group.
- 5.2.5 **Founding** is one request: the GroupInfo of epoch 0 (the founder alone) and the first Commit, which adds
  every device of `H(r)` except the founder, and for a main session its agent device (a main session is founded
  with exactly one agent leaf; an empty seat arises only later, 5.2.8). If a KeyPackage of one of them cannot be
  had, the founding fails and is tried again with fresh ones (a claim is all or nothing; what was handed out stays
  used): a human device is never left out. A lost answer is retried with the same bytes. A human device founds a
  main session; the opener founds a helper session, without a human's approval, at most 32 live ones per main
  session.
- 5.2.6 **First contact.** A human device that joins a helper session checks that the founding Commit was made by
  P's agent leaf of that time and that the group obeys 5.2.3; otherwise it shows a finding, never opens the
  session's content and removes the offending leaves or closes the group. The check is the walk of 4.6, for which
  the device has learned the room's and P's past. Only a history that is the group's own closes the group: one
  whose every Commit verifies as MLS and that arrives at the device's first epoch (4.6), and in which a Commit
  breaks section 5 by the group's own word: read against the room epoch its signed note names, a helper session's
  against every agent leaf P had in that room epoch, and without its `RecoveryAuth`, which is stored beside the
  Commit. A served history that does not arrive there, or that fails only by what the hub says beside the Commits
  (a change number, their order, an attachment), is `bad-group` and says nothing about the group. A group so
  closed stays closed, whatever its leaves are later.
- 5.2.7 **A human device missing from a live session group** is added by any human device of that group (after
  joining by link: by its inviter, in every live session group, one Commit and one KeyPackage each). A device that
  holds the recovery code instead joins from outside with a recovery signature (8.4). There is no other external
  commit.
- 5.2.8 **Removal** of a human or agent device is one act of the removing device: the room Commit, then at once
  the Remove with the Cut in every live session group that holds the device (for an agent device: a takeover or an
  empty seat). It is not atomic. From the room Commit on, the hub ends the removed device's access (14.4) and
  refuses whatever it posts. A session group is **stale** while it has a leaf the current room state does not
  allow (a revoked key; in a helper session also an opener leaf that is not its main session's agent leaf), and a
  helper session also while it lacks its opener although its main session has an agent leaf. Nobody writes into a
  stale group, and the hub takes nothing for it (`stale-session`) but a join by 8.4 and the Commit that removes
  those leaves and adds the missing opener, with its `SealedKey`, and does nothing beside (no other Remove, no Add
  of a human device); a Commit or `SealedKey` naming an older room epoch is refused (`room-behind`). Any human
  device that sees a stale group commits what is missing, so a crash in the middle is finished by whoever comes
  next. The removed device keeps what it had already read.
- 5.2.9 **Update.** A human device commits an empty Commit in a live group when its leaf there is older than 7
  days, at most once a day; the updates that 7.2 and `epoch-full` ask for come on top. Agent and helper devices
  make no Commit for the sake of an update; the path of a Commit they may make renews their leaf as MLS requires.
  The cadence is the client's alone: the hub neither asks for an update nor limits them.
- 5.2.10 A session is **live** until a human device archives it (the register `session/<id>` for clients, and
  `POST /v1/groups/{group}/archive` for the hub); the hub then accepts nothing more for the group. Its Commits and
  founding GroupInfo are kept as long as any envelope of it. An archived session is not reopened; continuing it is
  a new session.

### 5.3 Takeover

- 5.3.1 A takeover replaces a main session's agent device, always: there is no way to keep both. The human device
  (a) removes the old device from `agents` in the room group: by 5.2.8 its main session and every helper session it
  opened are stale from that Commit on, and it can found nothing; (b) commits Remove of the old leaf and Add of the
  new agent device, which is in `A(r)`, in the main session group; (c) the same in every helper session of that
  main session, asking the hub for the list until none is stale: the new device is their opener.
- 5.3.2 With history (the default) the human device then sends the key handover of 7.1 in each of those groups;
  without history it sends none and may send one later. A handover is read by every leaf of the group at that
  moment.
- 5.3.3 While a main session has no agent leaf, its helper sessions wait without an opener (5.2.3); their helper
  leaves stay until the takeover.
- 5.3.4 An agent device never receives a key of the room group or of a session it is not a leaf of.
- 5.3.5 A helper device that lost its state comes back as a new device (4.3): the opener commits Remove of the old
  leaf and Add of the new one, then sends a key handover. A helper device's KeyPackage reaches its opener outside
  the hub (they run under one connector, or the opener's own channel to its subagent); the hub gives a helper
  device a token once it is a leaf. An agent device that lost its state is a new agent device: join by link and
  takeover (13.4).

### 5.4 Ordering

- 5.4.1 The hub accepts for a group and epoch exactly one Commit, the first valid one (`epoch-taken` for the
  others: fetch, process, build again). The hub gives every Commit, message and envelope of a room one running
  change number; a device processes everything in that order, across groups, and never skips a Commit, so that a
  session Commit always meets the room state it names. The hub serves a log per group: a client merges them by
  change number before it hands them to the core, which takes nothing behind what it has processed
  (`wrong-epoch`) but a Commit it still lacks for a group it joined late.
- 5.4.2 A Commit comes with: the GroupInfo of the new epoch, the Welcome if it adds, and the `SealedKey` (8.2); the
  Commit with its GroupInfo and Welcomes is at most 1 MiB.

## 6. Content keys

```
content_key(G, e) = MLS-Exporter("trommi content", "", 32)      in group G at epoch e
```

- 6.1 This is the only key derived from a group. It protects the stored content of G written in epoch e (section 9).
- 6.2 A device stores every content key it derived or was handed, durably, per group and epoch: MLS cannot export a
  past epoch again.
- 6.3 Nothing is ever re-encrypted or copied for a newcomer; keys are handed over, under 100 bytes per epoch.

## 7. MLS application messages

```
enum { key_handover(1), stroke_piece(2), work_trail(3), recovery_auth(4), (255) } MessageType;
struct { opaque group_id<V>; uint64 epoch; opaque content_key[32]; } EpochKey;
struct { uint8 version = 2; MessageType type;
  select (type) {
    case key_handover: opaque recipient[32]; EpochKey keys<V>; uint8 last;
    case stroke_piece: opaque board[16]; opaque piece<V>;
    case work_trail:   opaque turn[16]; uint32 number; uint64 time; opaque step<V>;
    case recovery_auth: opaque recipient[32]; opaque recovery_hpke_key<V>; opaque recovery_mac[32];
  }; } TrommiMessage;
```

- 7.0 A message is at most 48 KiB. The hub stores a group's Commits and application messages in one ordered log and
  refuses an application message whose epoch is not the group's current one (`wrong-epoch`: process the log,
  encrypt again). A receiver that cannot open one (it was not yet a member, or its state was rebuilt) skips it.
- 7.1 **Key handover.** In the room group: sent by the human device that added a human device, right after the
  Add, with every content key it holds for every group of the room, in as many messages as needed (at most 400
  keys each), the final one with `last` = 1; any human device sends it again on the newcomer's request. In a
  session group: sent by a human device after a takeover, or by the opener after 5.3.5, with that group's keys
  only; and by a human device whose Commit added a human device to a session group (5.2.7, 3.7, 12.1.5), to each
  device it added, as soon as that Commit is merged, with the keys of that group's epochs before it: the room
  handover carries only what its sender held when it sent it, the session may have moved on before the Add, and
  a device that joined the room with the code no longer holds the code to open the session's `SealedKey`s. A
  handover message the hub refuses with `wrong-epoch` is encrypted again in the group's epoch then (7.0). `recipient` names the device it is for. A receiver accepts keys only from a human device, or in a helper
  session from its opener; an agent or helper device drops any key whose `group_id` is not the group the message
  came in. A receiver never replaces a key it already holds, and takes a key only for an epoch that group has
  reached (in a session group: its own epochs up to the current one). A wrong key opens nothing: content is
  signed. The sender keeps what it sent until the recipient's `heads` shows it reads.
- 7.2 **Stroke piece.** Room group, human devices: the points of a stroke still being drawn, about every 150 ms,
  at most 20 per second per device (`piece`: JSON `{ stroke, number, tool, color, width, points }`, at most 40 000
  bytes, no field `null`: `stroke` is 16 random bytes the drawer chose for this stroke, `number` counts its pieces
  from 1, `tool` `pen` | `marker`, `color`, `width` and `points` are those of a stroke in 10.5, the points being the
  ones added since the piece before). The sender posts it as relay-only: the hub passes it to the connected human
  devices, never stores it and does not put it in the log; a repeated post is passed on again, and a receiver, who
  opens a message once (3.6), ignores the copy. A device that cannot open one ignores it; the finished stroke
  arrives as a board item whose shape names `stroke` in `live`, and replaces what was shown of the pieces. After
  5 000 pieces in one epoch the sender commits an update (3.5).
- 7.3 **Work trail.** Session group, from its agent or helper devices: one step of the running turn (`step`: JSON
  `{ text, tool? }`, at most 40 000 bytes; `text` at most 30 000 bytes, `tool` 1 to 80, never `null`), `number`
  counting from 1 within `turn`. The hub keeps it 30 days. A device shows the steps it could open and keeps them
  locally; a device added later does not get them.
- 7.4 **Recovery auth.** Room group only, from a human device: `recovery_mac` (8.3) of the named recovery key. The
  inviter sends it to a device added by link right after its Add, the device that replaced the code to all
  (`recipient` zeros) right after 8.6; each writes the order to send it with its Commit (13.2) and the message,
  encrypted in the new epoch, when that Commit is merged; any human device that holds it sends it again on the
  request of one that does not (`POST /v1/requests`, kind `handover`). A receiver takes one addressed to itself or
  to zeros, sent by a device that was a human device in the message's epoch, naming the `recovery_hpke_key` of the
  room state of that epoch. A second, different value for a key it already holds one for is a finding
  (`equivocation`) and replaces nothing. A human device that does not hold the `recovery_mac` of the current
  recovery key founds nothing and commits nothing.

## 8. Recovery, and signing in on a new device (D1)

```
recovery code   32 random bytes, shown and read as in 8.0
recovery_sign   Ed25519 key pair from the seed ExpandWithLabel(code, "trommi recovery sign", "", 32)
recovery_hpke   DeriveKeyPair(ExpandWithLabel(code, "trommi recovery hpke", "", 32))        RFC 9180 section 7.1.3

recovery_mac    ExpandWithLabel(code, "trommi recovery mac", "", 32)                         known to human devices only

struct { opaque group_id<V>; uint64 epoch; opaque group_info[32]; } KeyContext; // group_info: RefHash("Trommi Group
                                                           // Info", the GroupInfo posted for that group and epoch)
struct { KeyContext context; uint64 room_epoch; opaque recovery_hpke_key<V>; HPKECiphertext sealed;
         opaque writer[32]; opaque mac<V>; } SealedKey;
  sealed = EncryptWithLabel(recovery_hpke_key, "TrommiSealedKey", KeyContext, content_key(group_id, epoch))
  mac    = HMAC-SHA-256(recovery_mac, "TrommiSealedKey" ‖ all fields before mac)     empty from a non-human writer
struct { KeyContext base; uint64 room_epoch; opaque room_state[32]; opaque joiner[32]; } RecoveryJoin;   // base: the
                                                           // group, epoch and GroupInfo the Commit builds on
struct { RecoveryJoin join; opaque commit[32]; opaque signature<V>; } RecoveryAuth;   // commit: RefHash("Trommi
  Commit", the external Commit);  signature = SignWithLabel(recovery_sign, "TrommiRecoveryJoin", join ‖ commit)
struct { opaque room_id[32]; opaque new_recovery_hpke_key<V>; HPKECiphertext sealed; opaque mac<V>; } RecoveryLink;
  mac    = HMAC-SHA-256(new recovery_mac, "TrommiRecoveryLink" ‖ all fields before mac)
  sealed = EncryptWithLabel(new_recovery_hpke_key, "TrommiRecoveryLink", room_id, OldRecovery)
struct { opaque hpke_secret[32]; opaque recovery_mac[32]; } OldRecovery;   // hpke_secret: what DeriveKeyPair was given;
                                                                           // the old signature key is not passed on
```

`HPKECiphertext` is RFC 9420's. OpenMLS: `OpenMlsCrypto::hpke_seal` / `hpke_open` with the `EncryptContext` as info,
`derive_hpke_keypair`, `Signer::sign` over the `SignContent`.

- 8.0 **The code's written form.** The 32 bytes are shown as 52 Crockford base32 characters
  (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`) in thirteen groups of four joined by `-`; bits most significant first; the
  last character holds one data bit and four zero bits. Input is accepted in any case, with spaces or hyphens,
  `O` read as `0`, `I` and `L` as `1`; anything else, another length or non-zero padding bits is refused
  (`bad-recovery-code`). There is no checksum: a mistyped code yields key pairs the room does not hold
  (`wrong-recovery`, 8.4).
- 8.1 A room is founded with `recovery_signature_key` and `recovery_hpke_key` in `TrommiRoom`; neither equals a
  device's key. They change only by 8.6.
- 8.2 Every Commit of every group, and every founding, comes with the `SealedKey` of the new epoch (at founding
  also of epoch 0), with the committer as `writer`, sealed to the room's `recovery_hpke_key` at the Commit's
  `room_epoch`; a room Commit that replaces the recovery keys seals its new epoch to the new key, with the new
  `recovery_mac`. `SealedKey.room_epoch` is the Commit's `room_epoch`; in the row of a room Commit that replaces
  the recovery keys it is the new room epoch, whose state holds the new keys; at a room's founding it is 0. The
  hub refuses a Commit without one for the right context and key, with a `mac` of 32 bytes from a human committer
  and an empty one from any other (`incomplete`); it cannot check the content or the `mac`'s value.
- 8.3 Human devices hold `recovery_mac` (the founder derives it; later ones get it by 7.4 or derive it from the
  code) and set `mac`; an opener cannot and leaves it empty. A human device that derives a content key for which
  the hub lists no `SealedKey` whose `mac` it can verify posts one, as its `writer`, with the `group_info` hash of
  the GroupInfo the hub holds, after checking that GroupInfo against its own group state. The hub takes a posted
  row only from a human device that is its `writer`, with a `mac` of 32 bytes, and keeps one per group, epoch and
  writer; `room_epoch` is the current one when posted (`room-behind`) and names the recovery key and
  `recovery_mac` in force.
- 8.4 **Joining with the code** (signing in on a new device, or recovery). The device derives both key pairs,
  signs in to the hub with `recovery_sign` (12.3) and fetches the room group's GroupInfo, whose `TrommiRoom` must
  hold exactly the two derived public keys (`wrong-recovery`): this ties the room to the code.
  It joins by external commit (3.4) with `join` = 1, posted and stored together with its `RecoveryAuth`, which
  every reader of the log gets with the Commit. It then joins every live session group the same way, each after
  verifying it as any reader does: from the founding GroupInfo (epoch 0) through its Commits in the hub's order
  against the room states it verified (5.2), joining only on a current GroupInfo that agrees with the state so
  reached (8.5); a row without `mac` in a session group blocks nothing. Members and the hub accept such a Commit
  if and only if, on top of every check of sections 3 to 5 (a revoked key does not return this way):
  `join.room_epoch` and `join.room_state` are the note's; `base` names the group, the epoch the Commit builds on
  and the GroupInfo posted for that epoch (the hub compares the hash with the GroupInfo it holds; a member is not
  handed that GroupInfo and checks group and epoch); `joiner` is the credential of the Commit's new leaf; `commit`
  is the hash of the Commit as posted; the signature verifies under the `recovery_signature_key` of the room state
  at the note's `room_epoch`; and, in a session group, the joiner is in `H(r)`. A stale group (5.2.8) takes such a
  join too: the leaves the room state does not allow stay for that one Commit, and the group stays stale until its
  Removes. No emoji: the code is the authority.
- 8.5 Before it joins, it checks the room.
  - **Anchor:** among the room group's `SealedKey`s that are well formed, name this room group and carry a `mac`
    valid under the `recovery_mac` derived from the code in hand (never one learned from a `RecoveryLink`), the
    one with the highest `context.epoch`. None: `wrong-recovery`; two that name different GroupInfos for that
    epoch: `equivocation`. It fetches the GroupInfo of that epoch, whose hash, group and epoch must be the row's,
    follows the room group's Commits after it as an observer (section 5), and joins only on a current GroupInfo
    that **agrees** with the state so reached: it verifies under OpenMLS against the observer's tree, its
    GroupContext is byte for byte the observer's, its confirmation tag is that of the last Commit followed, and
    its signer is that Commit's committer; at the anchor's own epoch it is the anchor's GroupInfo
    (`wrong-recovery` otherwise). So a hub that holds neither the `recovery_mac` nor a human device's signature
    key cannot hand it a room of its own making, and a later epoch whose row has no valid `mac` does not block
    it; that the state is the newest is not proven (section 17).
  - **Before the anchor:** the room states that older session Commits name (8.4), and the key that a
    `RecoveryLink`'s Commit replaced, it takes from following the room group as an observer from its founding
    GroupInfo (epoch 0) through the same Commits, and only if that walk, at the anchor's epoch, stands in the
    anchor's state: the GroupContext of the anchor's GroupInfo, byte for byte, with its tree and confirmation tag
    (`wrong-recovery` otherwise).
  - **Keys:** a row counts only if the room state at its `room_epoch` holds the `recovery_hpke_key` it names, and
    that `room_epoch` is not below the one under which its epoch began (room group: the epoch's own state, or the
    one before it if the key did not change between them; session group: the `room_epoch` of the Commit that led
    to the epoch, where the device verified it; a row for an epoch that a group it verified has not reached counts
    for nothing), so that a replaced code authenticates nothing for a later epoch. Per group and epoch, the rows
    with a valid `mac` must open to one key (`equivocation` otherwise, also when one does not open), which is
    taken; a row with an empty `mac` is taken only if that epoch has none with a valid one (content of those
    epochs is shown as unconfirmed); a row whose non-empty `mac` does not verify is ignored.
  - **Older codes:** a `RecoveryLink` belongs to the room Commit that put its `new_recovery_hpke_key` into
    `TrommiRoom`. It is taken if its `mac` verifies under that key's `recovery_mac` and the key pair derived from
    the opened `hpke_secret` has the public key the room state held before that Commit (`wrong-recovery`
    otherwise); its `OldRecovery` opens and authenticates the rows sealed to that older key, and so on back.
  - It keeps `recovery_mac`, and forgets the code and the two key pairs once the join, and in a recovery 8.7, has
    finished.
- 8.6 **Replacing the code** is one request that the hub applies whole or not at all: a room Commit (by a human
  device that holds the current code) with new recovery keys, never ones the room held before, its `RecoveryLink`,
  and the account's new sealed copies: one under the way in used just now (password or passkey; after a recovery
  with the Emergency Kit words or the bare code, under a password or passkey set anew in the same request) and one
  under a new Emergency Kit; every other way in is removed and set up again by the person. The device then sends
  the new `recovery_mac` (7.4). The app asks for this after a human device was removed that is not in the person's
  hands, and always in 8.7.
- 8.7 **Recovery** when every device is lost. The device opens a recovery at the hub (from then on, for ten
  minutes, the room takes nothing else: no Commit, founding, archiving, envelope, sealed key or account change),
  and joins by 8.4 the room group and every live session group. It then commits in the room group the removal of
  every other human device together with 8.6, and after that, against the new room epoch, in every live session
  group (main sessions before their helper sessions) the Remove of every leaf that the new room state, and for a
  helper session its main session's state, does not allow: the other human devices, and any revoked agent leaf or
  outdated opener leaf that an interrupted removal or takeover left. Every Remove carries the Cut: the head of that
  device's chain in that group as the new device verified it from number 1 through pruned envelopes fetched from
  the hub (0 and zeros if none; a provisional envelope moves no Cut): it reads those chains against the past its
  walk of each group gave it (4.6), and a chain that does not hold (`gap`, `chain-break`, a second envelope under a
  number) ends the recovery, since no Cut is taken from it. The hub publishes all of it at the end or none of it,
  and only if no live group is stale then. While it runs the room may hold 1001 human devices. Agent devices stay
  unless the human removes them.
- 8.8 **The account** (e-mail; password or passkey; Emergency Kit words; the three sealed copies of the code) is
  8.9, with its known answers in `account-vectors.json` and `vectors/account.json`. Its own refusals (`bad-email`,
  `weak-password`, `bad-kdf`, `bad-recovery-words`, `bad-recovery-code`, `no-prf`) arise on the device; section 16
  names them beneath its tables.
  - 8.8.1 Every account has an account id: 16 bytes (a UUID) that the hub mints when the account is made, a public
    value. Its text is the canonical UUID text, 36 characters: the bytes in order as lower-case hex with a hyphen
    after the 4th, 6th, 8th and 10th byte (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`). A client reads exactly this
    text and nothing else (upper case, braces, a missing or misplaced hyphen, another length: `bad-format`) and
    gives no bit of the 16 bytes a meaning. The text is printed on every Emergency Kit.
  - 8.8.2 An account may have no e-mail: it then has no password, and its ways in are its passkeys and its kit.
    The salt of 8.9 then has its second form, used for the kit's two keys only:

    ```
    salt = SHA-256("trommi/v1/account-salt" 0x00 ‖ email)            an account with an e-mail (8.9)
    salt = SHA-256("trommi/v1/account-salt/id" 0x00 ‖ account_id)    an account without one; account_id is the 16 bytes
    ```

    Which form applies follows from the account alone: with an e-mail always the first, and its id is then only a
    second way to name the account and enters no derivation; without an e-mail the second. Everything behind the
    salt is 8.9 unchanged: `kitAuth`, `kitWrapKey` with their labels, the sealed copy and its `aad`. No master
    key is derived from an account id. A passkey's copy uses neither salt (its key is salted with the room id).
    The two hash inputs differ at the byte after `trommi/v1/account-salt` (`0x00` against `/`), whatever the
    e-mail and the id: the same words under an e-mail and under an id give unrelated keys.

### 8.9 The account

An account (an e-mail with a password, passkeys or both, and an Emergency Kit) is a way into a room: each way
opens a sealed copy of the room's recovery code, with which a new device joins (8.4). A hub never sees the
password, the kit's words, a prf output or the code. The code that implements this section is
`core/src/account.rs`. This section does not use MLS's labelled functions: its primitives and labels are fixed
bytes.

| Purpose | Primitive | Parameters |
| --- | --- | --- |
| Hash | SHA-256 | |
| KDF | HKDF-SHA-256 (RFC 5869) | extract and expand, always both |
| Password KDF | Argon2id | as below |
| AEAD | AES-256-GCM | 96-bit nonce, 128-bit tag appended to the ciphertext |

A label is the ASCII string given, followed by one `0x00` byte; each has one use.

- `H(label, data…)` = SHA-256(label ‖ 0x00 ‖ data…)
- `KDF(ikm, salt, label, context, n)` = HKDF-SHA-256 with info = label ‖ 0x00 ‖ context, n bytes

| Label | Use | Label | Use |
| --- | --- | --- | --- |
| `trommi/v1/account-salt` | H: account salt | `trommi/v1/recovery-auth` | KDF: kit auth key |
| `trommi/v1/account-auth` | KDF: auth key | `trommi/v1/recovery-wrap-key` | KDF: kit wrap key |
| `trommi/v1/account-wrap-key` | KDF: password wrap key | `trommi/v1/passkey-wrap-key` | KDF: passkey wrap key |
| `trommi/v1/account-wrap` | aad prefix: sealed copy of the code | `trommi/v1/account-salt/id` | H: salt of an account without an e-mail (8.8.2) |

`trommi/v1/passkey-prf` is not a label: its UTF-8 bytes, without `0x00`, are the fixed WebAuthn prf input
(8.9.7).

```
salt   = H("trommi/v1/account-salt", email)
master   = Argon2id(password as NFC UTF-8, salt, m = 65536 KiB (64 MiB), t = 3, p = 1, 32 bytes)
K(ikm, l)  = KDF(ikm, salt, l, context = empty, 32)
authKey   = K(master, "trommi/v1/account-auth")   wrapKey   = K(master, "trommi/v1/account-wrap-key")
kitAuth   = K(r, "trommi/v1/recovery-auth")   kitWrapKey = K(r, "trommi/v1/recovery-wrap-key")
passkeyWrapKey = KDF(prf(32), salt = roomId(32), "trommi/v1/passkey-wrap-key", context = credentialId, 32)
sealedCopy = 0x02 ‖ nonce(12) ‖ AES-256-GCM(key, nonce, aad, code(32))   61 bytes
aad   = "trommi/v1/account-wrap" ‖ 0x00 ‖ roomId(32) ‖ what ‖ [ credentialId ]   iff what = "passkey"
what   = ASCII "password" (key = wrapKey) | "recovery" (kitWrapKey) | "passkey" (passkeyWrapKey)
```

- 8.9.1 E-mail: (1) leading and trailing U+0020 and U+0009–U+000D are dropped; (2) every character left is
  U+0021–U+007E, anything else is refused, never mapped; (3) A–Z become a–z; (4) at most 254 characters, exactly
  one `@`, 1 to 64 characters before it, after it a `.` with 1 to 190 characters before and 2 to 63 after.
  Otherwise `bad-email`.
- 8.9.2 A password may be used if its NFC form has at least 12 code points (`weak-password`).
- 8.9.3 `code` is the 32 raw bytes of the recovery code (8.0); the nonce is 12 random bytes. A copy of another
  length or first byte (`0x01` included) is refused (`bad-format`), not converted. A copy that does not open:
  `wrong-login`, for the kit `wrong-recovery`.
- 8.9.4 `authKey` goes to the hub at sign-in, which keeps only a slow hash of it; `kitAuth` is what the hub checks
  before it hands out the kit's copy. The wrap keys never leave the device.
- 8.9.5 Kit: 12 uniformly random words of the list of 7772 words in `core/src/account.rs` (about 155 bits; no
  slow KDF). `r` = UTF-8 of the lowercase words joined by one space. Input is lowercased and split at anything but
  a–z; other than 12 words of the list is `bad-recovery-words`.
- 8.9.6 The key derivation record is pinned to `{ alg: "argon2id", v: 1, m: 65536, t: 3, p: 1 }`: a record from a
  hub is accepted only if these five fields are exactly so (other fields are ignored); none means the pinned set;
  a record above 1024 bytes, or anything else, is `bad-kdf` and nothing is derived with it.
- 8.9.7 Passkey: `prf` is the 32-byte output of the WebAuthn prf extension over the fixed input UTF-8
  `trommi/v1/passkey-prf`, a client constant never chosen by a hub; without it `no-prf` and nothing is sent. The
  user handle is 32 random bytes. A passkey challenge lasts two minutes and one use.
- 8.9.8 An account is made with its kit in one request: none exists without one. A new kit replaces the one
  before. Changing the password re-wraps the code and replaces `authKey`; nothing else is re-encrypted.
- 8.9.9 A hub gives one answer for an unknown e-mail and a wrong password (`wrong-login`), and refuses to remove
  the last way in (`last-way-in`).

## 9. Stored content (D2)

Every stored item (Chat message, card version, answer, take back, permission request, verdict, Note version, Artifact
version, board item, register value) is one envelope, chained per sender and group. Nothing else is stored content.

```
enum { item(1), version(2), answer(3), request(4), verdict(5), register(6), take_back(7), (255) } Kind;
struct {
  uint8 version = 2;  Kind kind;  uint8 flags;              // flags: bit 0 = push; other bits refused
  opaque group_id<V>;  uint64 epoch;                        // which content key
  opaque sender[32];  uint64 seq;  opaque prev[32];         // the sender's chain in this group
  opaque recipient[32];  uint64 time;                       // a device id or zeros; the sender's clock
  select (kind) {
    case item:      uint8 timeline_kind;  uint8 timeline_scope;  opaque timeline_ref[16];
    case register:  opaque register_id[16];
    default:        opaque object_id[16];  uint8 object_type;  uint8 object_state;  uint8 urgency;  uint64 answered_at;
                    opaque object_ref[32];
  };
  opaque file_ids<V>;                                       // 16 bytes each, at most 255
} Header;
struct { uint8 form;  Header header;  opaque nonce[12];
  select (form) { case full(1): opaque ciphertext<V>;  case pruned(2): opaque ciphertext_hash[32]; };
  opaque signature<V>; } Envelope;
struct { uint8 version = 2;  opaque bind<V>;  opaque payload<V>; } Body;

padded        = Body ‖ zero bytes up to the next of 256, 512, 1024 … 65536 bytes
ciphertext    = AEAD.Seal(content_key(group_id, epoch), nonce, aad = Header, padded)     the suite's AEAD; nonce random
envelope_hash = RefHash("Trommi Envelope", Header ‖ nonce ‖ SHA-256(ciphertext))
signature     = SignWithLabel(sender's device key, "TrommiEnvelope", envelope_hash)
object_id     = first 16 bytes of RefHash("Trommi Object", group_id ‖ sender ‖ seq)       of the object's first version

bind, by kind (empty for the others):
answer     struct { opaque object_id[16]; opaque version_hash[32]; opaque choices<V>; }  // choices: vector of opaque<V>, each ≤ 256 bytes, ≤ 64
request    struct { opaque request_id[16]; uint64 expires_at; }
verdict    struct { opaque request_id[16]; opaque request_hash[32]; uint64 expires_at; uint8 verdict; }   // 1 allow, 2 deny
take_back  struct { opaque object_id[16]; opaque previous_hash[32]; opaque version_hash[32]; }
```

| Field | Values |
| --- | --- |
| `timeline_kind`, `timeline_scope` | 1 chat, 2 board; 1 card, 2 session, 3 desk; only the pairs chat/card, chat/session and board/desk exist. `timeline_ref`: object id, session id or board id |
| `object_type` | 1 card, 2 note, 3 request, 4 artifact; fixed by the first version |
| `object_state`, `urgency` | 1 open, 2 answered, 3 closed; 0 low, 1 normal, 2 high, 3 critical |
| `answered_at` | ms, 0 while open; display only |
| `object_ref` | version: the `envelope_hash` of the version before it (zeros for the first), equal to the payload's `previous_version_hash`. answer, take back: `bind.version_hash`. verdict: `bind.request_hash`. request: zeros |

- 9.0.1 `seq` starts at 1 per sender and group; `prev` is the `envelope_hash` of the sender's previous envelope in
  that group, zeros for the first. A device never signs two envelopes under one number.
- 9.0.2 `payload` is one UTF-8 JSON object in which no object names a key twice; a `schema_version` above 2 is
  `newer-version`, none is read as 2. The padding is exactly as given and all zero. `version_hash`, `request_hash`,
  `previous_hash` are the `envelope_hash` of the version answered, the request, the answer taken back. In `object_id`,
  `group_id` is the group id's 32 or 48 bytes as they are and `seq` a `uint64`; a request's `request_id` is its
  `object_id`. An answer's `choices` are the keys of the chosen options in UTF-8; a `choices` in its payload equals
  them. The signature is 64 bytes.
- 9.0.3 The signature covers header, nonce and ciphertext hash, so a pruned envelope verifies and carries the chain.
- 9.0.4 Kinds 8 to 255 are reserved: writers and the hub (`bad-format`) refuse them; a reader parses one with the default block, whose values it does not judge,
  verifies and chains it, applies nothing and shows "needs a newer Trommi". A `version` above 2 is `newer-version`.
- 9.0.5 **Receiver checks, in this order.** (1) Encoding, flags, values (`bad-format`); the room (`wrong-room`).
  (2) The receiver has processed the group up to `epoch` (`group-behind`). (3) The sender was a leaf of the group in
  `epoch` (`not-member`). (4) A removed sender: `seq` above its Cut is `removed-sender`; at the Cut the hash is the
  Cut's (`equivocation`). (5) The signature (`bad-signature`). (6) The chain: `seq` is the last accepted plus one and
  `prev` matches; else `replay`, `equivocation` (same number, other hash), `gap`, `chain-break`. Up to here a failure
  consumes nothing; from here on the chain has advanced, whatever follows. (7) The sender may write this item (9.2:
  `forbidden`). (8) Freshness: an envelope of an older epoch is `wrong-epoch` when the receiver processed the Commit
  that ended that epoch more than 2 minutes ago; when reading back, when `time` is more than 5 minutes after that
  Commit's `time`. (9) Decryption with the content key of that group and epoch (`no-key`; a pruned envelope:
  `pruned`; a sealed body beyond the largest padded size: `too-large`; else `decrypt-failed`, `bad-format`,
  `newer-version`). An envelope that fails 7, 8 or 9 is chained and
  never applied.
- 9.0.6 Every chain is verified from number 1: a device fetches a sender's envelopes in pruned form where it does
  not need the bodies. An envelope of an epoch before the device's first epoch in the group is `group-behind`
  (check 2) and consumes nothing until the device has learned the group's past (4.6); from then on it is checked
  like any other, and, since the device did not process the Commit that ended such an epoch when it came, with
  the freshness of reading back (check 8: its `time` against that Commit's `time`), wherever it stands in the
  hub's order. An envelope that took its place without its body (pruned as served, or its key not yet handed
  over, 7.1) gets its body when the device is handed the same envelope in full again, out of order: a device keeps
  no ciphertext. The one shortcut is a board snapshot's frontier (10.3). An envelope fetched out of order (a
  page of a Chat, an object) is shown as provisional once it passes checks 1 to 5 and 7 to 9 against the group
  state of its epoch (of check 7 what the sender's role decides; the object's state is judged when the chain
  arrives, in the hub's order); it is accepted when the chain reaches its number with the same hash (`hash-mismatch`
  otherwise), and no command is executed before that.
- 9.0.7 **`heads`.** Each device writes the register `heads` in each group when it comes online and a head changed,
  and at most every 10 minutes while connected: `{ "<sender>": [seq, envelope_hash] }` for every chain it accepted
  there, its own too. A head changed when another sender's did since the device last wrote `heads` there, or
  when the device itself wrote anything but `heads` since: the `heads` envelope moves its own chain and calls
  for no other one. A reader that holds less than a named head fetches; if the hub has nothing, the finding is `withheld`;
  another hash under the same number is `equivocation`.
- 9.0.8 **Void records.** The hub takes a new envelope in the group's current epoch, or in the one before within 2
  minutes of the Commit's arrival (its check 8). An envelope that passed checks 1 to 6 at the hub and is then refused with `forbidden`,
  `wrong-epoch`, `stale-session`, `epoch-full` or `too-large` is stored pruned as a void record: it keeps the
  sender's number, the refusal says `voided: true`, and every read route serves it with its `void_code`. Receivers
  chain it and apply nothing; a void of another sender whose reason they cannot re-check from the header and their
  group state is the finding `hub-voided-other`: `forbidden` is checked again by check 7, `wrong-epoch` by the
  epoch having ended, `stale-session` and `epoch-full` only by a receiver that processes in the hub's order, and
  `too-large` (a sealed body beyond the largest padded size) not at all, since the record is pruned. Other refusals
  take no number. A device whose envelope was refused without a void record sends the same bytes again: it signed
  that number (9.0.1) and gives it to no other envelope. `too-large` is the hub's alone to refuse: a device takes what the hub serves as stored by its
  header, the same in full and in pruned form, and a body that is too long does not open (check 9; section 17).
- 9.0.9 **Command gate.** An agent or helper device acts on an envelope only if: it passed all nine checks; the
  sender is a human device now; `recipient` is this device; its epoch is the group's current one, or the one before
  and the Commit between is at most 2 minutes old; the kind is item on a chat timeline, answer, verdict or take
  back. For the last three the bind's object or request id equals the header's `object_id` and names an object of
  this group that this device owns (9.2). Answer: the object is an open card, `version_hash` is its current
  version; `answer_action` `answer` carries at least one choice if the card has options, more than one only with
  `allows_multiple`, each a distinct option of that version; `read` and `shred` carry none. Verdict: the request is
  pending, `request_hash` and `expires_at` are its own, the clock is before `expires_at`. Take back: `version_hash`
  is current, `previous_hash` the answer in force. The device records each command by `envelope_hash` before acting
  and never acts twice; one whose effect is uncertain after a crash is reported, not repeated.
- 9.0.10 **Cuts.** A Commit that removes a leaf names that device's last envelope in this group that the remover
  accepted (0 and zeros if none). The device's chain ends there for everyone: the hub and every receiver refuse
  what lies beyond (check 4). The Cut stands for ever for whatever the device signed for an epoch before it was a
  leaf again: if the same key is added to that group again (3.7), its chain goes on from the Cut, with envelopes of
  the epoch that added it or a later one only (the device signs the numbers after the Cut anew: what it had
  signed beyond the Cut is void for everyone, the one case in which it gives a number to a second envelope,
  9.0.1); the hub adds a key again only if it holds nothing of it beyond its
  Cut (`bad-commit`), and decides this for everyone: a member can tell only for what it was served, does not
  merge such a Commit if it holds more than the Cut names, and otherwise relies on the hub. When a key that came
  back is removed again, the Cut of that removal takes the place of the earlier one and names the chain up to
  it. A board's applied frontier beyond a Cut falls back to it (10.3); what the hub had already taken beyond it stays stored as evidence, is served only on
  the chain route marked `cut`, and leaves every index, object state and share as if it had never come. Clients
  drop it from what they show. What an agent already did on such an envelope is not undone.
- 9.0.11 The hub runs checks 1 to 8 without the body, the rules of 9.2, `stale-session` (5.2.8) and `epoch-full`,
  and takes an envelope only in full form (`bad-format` for a pruned one), only from the signed-in device that
  signed it (`wrong-sender`), an agent device only under its current lease (`lease-lost`).

### 9.2 Who may write what

| Item | Allowed sender |
| --- | --- |
| card, request, Artifact version | version 1: an agent or helper device of the session, which then owns the object. Later versions: the owner; once the owner is no longer a leaf, the session's agent device (in a helper session: its opener) owns it, for good: also if the same key is a leaf of the group again (9.0.10). Each version names its predecessor (`previous_version_hash`) |
| Note version | any human device |
| answer, take back, verdict | a human device, `recipient` = the object's owner |
| Chat on `session/<S>` | S's agent or helper devices; a human device, addressed to S's agent device (helper session: its opener); while the session has no such leaf, with `recipient` zeros |
| Chat on `card/<X>` | as for the session X belongs to |

- 9.2.1 **Object state, the same at the hub and on every client**, replayed from headers alone (pruned envelopes
  count, void and cut ones do not), each envelope judged against the state just before it. A first version (kind
  version for a card, Note or Artifact; kind request for a permission request, which has no later version) is taken
  if its `object_id` is the one section 9 derives from it, `object_ref` is zeros and the sender may create that
  type; the sender owns the object, the state is open. A later version is taken if `object_ref` is the current
  version and the sender owns the object; it becomes current with its `object_state` (open or closed). An answer
  is taken if `object_ref` is the current version and the state is open: the state becomes the answer's (answered
  or closed). A take back is taken if `object_ref` is the current version and the state is answered: open again. A
  verdict is taken if `object_ref` is the request and it is open: closed. On every envelope the header's
  `object_type` is the object's and its `object_state` the state the envelope leaves (a first version and a
  request: open); answers and take backs belong to cards, verdicts to requests. An envelope that passed checks 1 to
  8 counts even if its body does not open (check 9): the hub cannot tell, and all must agree. Anything else is `forbidden` (a void
  record) and changes no state, deadline, file or share. A device stores the transition when it takes the envelope, and its
  command decision (9.0.9, judged against that same earlier state) before it acts. Notes are the exception: any human
  device writes a version on any other; clients choose the current one as for registers (9.3.2), the hub keeps the
  newest by arrival and prunes Notes as 9.4 says.
### 9.3 Registers

- 9.3.1 A register value is `{ name, value, lamport }`; `value: null` deletes. The header names a `register_id`: 16
  random bytes the writing device chose for that name and reuses for it; the hub sees no name.
- 9.3.2 The current value of a name is the one with the highest (`lamport`, sender id, sender's envelope number)
  among the senders allowed to write it. `lamport` is one above every lamport the writer had seen in that group; one
  above 2^48, or more than 2^24 above the largest seen, counts as 0.
- 9.3.3 Names. Room group, shared by human devices: `desk/<id>` (`name`, `created_at`, `order`, `crown`, `goals`: one
  text of at most 20 lines separated by a line feed, each of at most 200 characters, which are Unicode scalar
  values; null or absent for none; every account has at least one desk: a human device writes `desk/main` =
  `{ name: "Personal", created_at: 0 }` when it founds the room and whenever it finds no desk, and the last desk is
  not removed), `session/<session>` (`name`, `desk`, `archived`, `icon`,
  `position`: its place in the sidebar's order, a whole number), `crown`, `kit`,
  `draft/<object>`, `snooze/<object>`, `duck/<object>`, `read/<timeline>`, `board_snapshot/<board>`. Any group, own
  device only: `device/<device id>` (`device_name`, `platform`, `folder?`, `host?`), `heads` (9.0.7). Session group,
  agent or helper device: `profile` (`model`, `task`, `icon`, `agent_name`), `status_line/<id>` (`label`, `state`,
  `detail`, `object_id?`), `heard`, `alert/<envelope hash>`. Session group, human devices: `goals`. A device id in
  a name, in `heads`, in a frontier (10.2) and in a shape id (10.1) is base64url, like every byte string in JSON
  (section 2). A name is at most 255 bytes. A writer that uses one `register_id` for two names, or two for one
  name, is not read (`bad-format`).
- 9.3.4 **Goals.** The Desk's Goals live in `desk/<id>` in the room group. For each live main session on that Desk
  every human client keeps `goals` in the session group equal to `{ desk_id, desk_name, goals }` (null without
  goals), writing it when it differs and again after a Commit that added an agent device. An agent reads `goals` of
  its main session; helper sessions get none. In both values `goals` is the text of 9.3.3 with its limits: a
  writer refuses more (`too-large`; a `goals` that is no text: `bad-format`), and a reader does not take such a
  value, so that the one before it stays current. A device that comes later may find that writer's earlier
  value pruned (9.4) and keep another writer's value instead: a writer refuses such a value, so only a faulty
  writer causes this.
- 9.3.5 A value is at most 4 KiB as compact JSON. `heads` and `board_snapshot/<board>` list one entry per sender and
  are bounded by the payload limit instead. The limit holds for a Desk's value and for `goals` beside the limits of
  the Goals in them: twenty full lines of letters beyond ASCII, or beside a long name, do not fit and are
  `too-large`.

### 9.4 Kept and removed

Pruning removes an envelope's body and keeps header, nonce, ciphertext hash and signature (9.0.3): chains,
object states and void records stay as they were. The hub prunes nothing except:

- 9.4.1 **Settled objects.** 30 days after an object's newest state became answered or closed (the hub's arrival
  time; a reopening cancels it), the hub prunes the bodies of that card's, request's, Artifact's or Note's
  envelopes and of its card Chat and deletes its files; an Artifact's files are deleted at once when it is closed.
  A Note is closed by a version that deletes it; the hub judges a Note by arrival, so a concurrent open version
  that arrived before the deleting one is pruned with it.
- 9.4.2 **A writer's older values.** When it takes a register value, the hub prunes the bodies of the same
  writer's earlier envelopes with the same `register_id` in that group; when it takes a Note version, those of
  the same writer's earlier versions of that Note. A writer's lamport is above every one it wrote before
  (9.3.2), so none of them can be current again. Files that only such pruned envelopes named are deleted (an old
  board snapshot's file).
- 9.4.3 **What every board snapshot covers.** Board items whose bodies no possibly current snapshot needs (10.2,
  10.9), and the files only they named that no snapshot keeps.

A device keeps what it shows and what it needs to write a snapshot; it drops what the hub prunes in the same way.

## 10. The Scribble Board

- 10.1 One board per Desk and one for "All desks". A Desk's id is 16 random bytes and is its board's id; the board
  of "All desks" has the id `616c6c2d6465736b7300000000000009`. Items
  are an add-only set; erase, move and send away name shape ids `<sender>/<envelope number>/<index>`: the sender in
  base64url, the two numbers in decimal; sender and number are those of the signed header of the item that adds
  the shape, the index its place in that item; the id of a shape that an item adds is never read from its body. Adding, erasing
  and moving commute (10.7). The bodies, the packed points of a stroke and the merge are `trommi-core`'s, the same
  code on every device (10.5 to 10.8); the samples of `strokes.json` stay valid for the packed points.
- 10.2 **Snapshot.** A human device writes the board as it is now (no erased or sent-away shapes) as a file (gzip
  JSON `{ v: 3, shapes, frontier, gone, moved }`, 10.8) and points `board_snapshot/<board>` at it: `{ attachment, frontier, change }` (`change`: the hub's change number the writer
  had processed).
  `frontier`: per writer the number and hash of its last envelope in the room group that the snapshot covers, in
  the shape of `heads` (9.0.7). Before writing the register value and once it is taken, the writer tells the hub
  what the snapshot covers and keeps (10.9).
- 10.3 **Loading.** A device takes the newest snapshot (9.3.2; registers come with the Desk) and the board's items
  from 1 000 changes before its `change` on, and verifies each
  writer's chain from the frontier on: it fetches that writer's envelopes after the frontier in pruned form,
  checks that they link (`gap`, `chain-break`), and that every one naming this board was served (`withheld`; a
  served item that is not the envelope its writer's chain has under that number: `hash-mismatch`, at the
  frontier's number `equivocation`). A snapshot is accepted only if its frontier is at or beyond the one applied
  (`replay`; another hash under an applied number: `equivocation`): the frontier of the snapshot the device
  loaded last for that board, not the items it applied after it, so that the same snapshot loads again and the
  board is built anew from it, and only if it does not reach beyond the Cut
  of a removed writer (`removed-sender`): such a snapshot holds shapes that are to vanish (9.0.10). The frontier
  is a shortcut only for a writer of whom the device holds nothing: where it holds a head of that writer (the
  frontier it applied last, with the chain it verified after it), it fetches the writer's envelopes from that
  head on, and they lead to the new frontier's envelope (`withheld` if they end before it, `equivocation` if
  they have another one under its number). A writer's chain that began at a frontier goes on from it: the
  envelope after the frontier is the next one taken. What that writer wrote up to the frontier, its Note versions
  and register values too, the device does not hold; it can read that chain from number 1 at any time later
  (9.0.6), in its order, and the envelope it then meets under the frontier's number must be the frontier's
  (`equivocation`: the snapshot and the chain disagree, and the chain stays begun at the frontier). Until then a
  snapshot whose frontier lies below the one a chain began at is `gap`. An item the frontier covers may be served
  pruned (9.4.3); it is chain-checked and skipped like any covered item. An item after the frontier that is
  served pruned is covered by a snapshot the device does not hold yet: it catches up, takes the newest snapshot
  and loads the board again; a pruned item that no snapshot it can get covers is `withheld`.
- 10.4 A picture is a reference in the snapshot (position, size, attachment); its file is fetched when in view.
- 10.5 **Item bodies** (JSON, `schema_version` 2), by `content_type`. `strokes`: `{ strokes: [shape] }`, 1 to
  1 000 shapes, each by its `tool`: `pen` | `marker`: `{ color, width, points, live? }` (`live`: 16 bytes, 7.2);
  `text` | `sticky` | `voice`: `{ at: [x, y], text, size, color, wrap? }` (`at`: the top left corner);
  `image`: `{ rect: [x0, y0, x1, y1], attachment }` (9.1.1 with `file_id`, `file_key`, `sha256`, `file_name`,
  `media_type`, `total_size`, `width?`, `height?`); every shape may carry `z` (a whole number, the layer) and
  `group`. `erase`, `send_away`: `{ shape_ids }`; `move`: `{ shape_ids, offset: [dx, dy] }`; 1 to 2 000 ids, none
  twice. Every position, length and offset is a whole number of 1/16 board unit (a board unit: 1 CSS pixel at
  100 % zoom, 1 point in PencilKit; x to the right, y down) from −2^31 to 2^31 − 1, as is `z`, written without
  fraction, exponent or a sign before 0; `width` and `size` are 1 to 16 000, `wrap` is above 0, `text` at most 20 000 bytes, `color` 1 to 40, `group` 1 to 80, `file_name` and
  `media_type` 1 to 255. A stroke carries no transform: its writer applies one to the points before writing. A
  reader refuses (`bad-format`) an unknown `content_type` or `tool`, a shape that names an id, a field that
  belongs to another tool or content type, a field of these that is `null`, and a `file_key` written with an
  escape; a body of a higher `schema_version` is `newer-version`. A device
  that could not read an item of a board (`newer-version`, `no-key`) writes no snapshot of that board until it has
  loaded one or built the board again with the item.
- 10.6 **Packed points.** `points` is the base64url of: one byte of flags (bit 0: every point carries azimuth
  and altitude; bit 1: the force was simulated, the input had no pressure; any other bit is refused), then per
  point: x and y, each as zigzag LEB128 of the difference to the point before in 1/16 unit modulo 2^32 (the first
  point: to zero); the time as LEB128 of the milliseconds since the point before (the first point: since the
  stroke began); the force as one byte, 0 to 255 for 0 to 1; with bit 0, azimuth as one byte (× 2π/256) and
  altitude as one byte (× (π/2)/255). 1 to 10 000 points; every number is below 2^32, as is the sum of the times,
  and written in the fewest bytes, so points have exactly one packed form (`bad-format` otherwise). The points
  are the control points of a uniform cubic B-spline with clamped ends, as PencilKit's.
- 10.7 **Merging.** Positions are whole numbers of 1/16 unit modulo 2^32. A shape is added once, under its id.
  Erase and send away remove a shape for good, also one whose item has not arrived yet. A move adds its offset to
  every position of each shape it names, modulo 2^32, also to one that has not arrived yet; on an erased shape it
  does nothing. A device applies each writer's items in the order of that writer's chain and each item once.
  The board is then the same on every device that applied the same items, whatever the order of arrival between
  writers. When a Cut (9.0.10) ends a writer's chain below an item the board has applied, the device builds the
  board again from the items that remain.
- 10.8 **Snapshot file.** `shapes`: every shape on the board as in 10.5 with its `id`, where its moves have put
  it, ascending by id (sender, number, index). `frontier`: the register's (10.2). `gone`: the ids that were erased
  and lie beyond their writer's frontier, ascending; `moved`: `[id, dx, dy]` for the summed moves of such ids that
  are not in `gone`, ascending, a sum of nothing left out: an item after the frontier may still add these shapes.
  The JSON is at most 64 MiB, which whoever decompresses the file enforces. The writer's frontier covers no board
  item that its board has not applied. A device refuses
  (`bad-format`) a file whose frontier is not the register's, that holds a shape beyond the frontier, an id twice
  or out of order, an entry of `gone` or `moved` that the frontier covers, or a move by nothing; a `v` above 3 is
  `newer-version`. A board loaded from a snapshot skips every item its frontier covers. A snapshot is the word
  of the human device that wrote it, as an erase is: 10.3 shows that what the hub served after the frontier links
  and lacks no item up to the heads the device knows (section 17), not that the shapes are what the items before
  the frontier gave. A device that doubts one reads the chains from
  number 1 (9.0.6).
- 10.9 **Pruning a board.** A human device tells the hub about each snapshot it writes, in two posts of
  `{ frontier, files }`: `frontier` the register's (per writer `[seq, hash]`), `files` the ids of every file the
  snapshot's shapes name (pictures, posters), at most 20 000. The first, the declaration, comes before the
  register value is written; without it taken the device writes no snapshot. The second comes once the hub took
  the value and names it, `snapshot: [seq, hash]`: the device's own register value, the newest of its register,
  not cut; an older value than the one the device's post is already bound to is `replay`. A frontier that names
  an envelope the hub does not hold or under another hash is `bad-format`, one beyond a removed writer's Cut
  `removed-sender`. The hub keeps per device and board its bound post (its time: the arrival of the value it is
  bound to) and its declaration (a later one keeps, per writer, the smaller number of both; the bound post
  answers it). It prunes, per writer, the board's items up to the smallest number that writer has in the posts
  that count (a post without that writer counts 0), and only while at least one bound post counts. A post counts
  while it is at most 30 days older than the newest one of the board and names nothing that a Cut left beyond
  its writer's chain; a removed device's post keeps counting, as its value within its Cut can still be current.
  Why this keeps what a loader needs: a device's frontiers only grow (10.3, `replay`), the current snapshot
  (9.3.2) is its writer's newest value, declared before it was written, so its frontier, or a smaller one of
  the same device, is among the posts from that moment on. A snapshot more than 30 days older than another
  device's is not current: that device was caught up when it wrote (it writes a snapshot only while it is
  connected and has nothing unsent), had loaded it and wrote a higher lamport. A pruned item's files are deleted
  unless a counting post or an envelope with its body names them. The hub learns from the posts that a snapshot
  of the board was written, the numbers it reaches and which files are still on it; it sees no shape.

## 11. Files, Artifacts, Share links (D3)

```
struct { uint8 version = 2;  opaque file_id[16];  uint32 chunk_size; } FileHead;       // chunk_size = 65536
file    = FileHead ‖ chunk_0 ‖ chunk_1 ‖ …
chunk_i = AEAD.Seal(file_key, nonce_i, aad = FileHead, plaintext[i × 65536 …])          the suite's AEAD
nonce_i = 0x00 0x00 0x00 ‖ uint64 i ‖ uint8 last                                        last = 1 on the final chunk
link    = https://<app>/artifact/<share_id>#<secret>.<file_key>.<sha256>                base64url parts
```

- 11.1 `file_key` is 32 fresh random bytes per file, used for nothing else; `file_id` 16 random bytes. An empty file
  has one empty chunk; every chunk but the last is full, and the last is empty only in an empty file
  (`bad-format` otherwise). A file cut at a chunk boundary fails: no final mark. The limit of 64 MiB counts the
  plaintext; stored, the largest file has 67 125 269 bytes.
- 11.2 `file_key`, the SHA-256 of the stored file, name and type stand only in the encrypted body that names the file
  (9.1.1); the header lists the `file_id`. A whole download is compared with the SHA-256 before it is decrypted
  (`decrypt-failed`); a download decrypted while it streams is compared when it ends, before its final chunk is
  opened, and what was handed out earlier counts only then; a read of single chunks (`Range`) relies on each
  chunk's own authentication.
- 11.3 A stored file never changes. It belongs to the group, and to the object if any, of the first envelope of its
  uploader that names it; an envelope of another group or object that names it, or of a device that neither uploaded it nor owns that
  object now, is refused (`forbidden`).
  Human devices of the room fetch it; an agent or helper device only while it is a leaf of that group; before an
  envelope names it, only its uploader and human devices. Uploading the same bytes again is answered like the first time, other bytes
  under a used id are refused (`replay`). It is deleted when no such envelope came within an
  hour, by its uploader or a human device, or with its object (9.4).
- 11.4 An **Artifact** is an object of a session: version 1 publishes, later versions change title, note or
  `shared_until`, a closed version revokes. It does not expire.
- 11.5 A **Share link** gives one file of an open Artifact to someone outside. Its maker (the session's agent or
  helper device, or a human device) registers `share_id` (16 random bytes), SHA-256 of `secret` (32 random bytes),
  the file and an expiry at most 180 days ahead. The hub serves that file's bytes to whoever presents `secret`, until
  expiry, revocation by the maker or a human device, or the Artifact's closing. The key never reaches the hub.
  In the link, `https://<app>` stands for the app's origin, written in the canonical form of 12.1.1; `share_id`
  and the three parts are the canonical base64url of 16, 32, 32 and 32 bytes, and nothing else is a Share link.
  A link is made with `/artifact/`; one with `/a/` in its place (the form of before) is read as the same link.

## 12. Joining

### 12.1 By link (D4)

```
link          = https://<app>/join#v1.<hub>.<room_id>.<secret>.<expires_at>   base64url parts; secret: 32 random
                                                                              bytes; expires_at: uint64 ms, 8 bytes
                                                                              big-endian (11 characters)
context       = room_id ‖ uint64 expires_at
invite_id     = ExpandWithLabel(secret, "trommi invite id",    context, 16)
mac_key       = ExpandWithLabel(secret, "trommi invite mac",   context, 32)
offer_mac_key = ExpandWithLabel(secret, "trommi invite offer", context, 32)

struct { opaque room_id[32];  opaque invite_id[16];  uint8 role;  opaque session_id[16];  uint64 expires_at;
         opaque commitment[32];  opaque inviter[32];  uint64 room_epoch;  opaque room_state[32]; } Offer;
struct { opaque room_id[32];  opaque invite_id[16];  opaque hub<V>;  uint8 role;  opaque key_package<V>;
         opaque offer_hash[32]; } Request;
struct { opaque invite_id[16];  opaque nonce[32];  opaque request_hash[32]; } Reveal;

commitment   = RefHash("Trommi Invite Commitment", invite_id ‖ nonce)        nonce: 32 random bytes, kept by the inviter
room_state   = RefHash("Trommi Room State", the room group's GroupContext at room_epoch)
offer_hash   = RefHash("Trommi Invite Offer", Offer)
offer_mac    = HMAC-SHA-256(offer_mac_key, Offer ‖ offer_signature)     the Offer's bytes as sent (177), then its
                                                                        signature (exactly 64 bytes); 32 bytes
mac          = HMAC-SHA-256(mac_key, Request)
request_hash = RefHash("Trommi Invite Request", Request ‖ mac)
signatures   = SignWithLabel(inviter, "TrommiInviteOffer", Offer);  SignWithLabel(new device, "TrommiInviteRequest",
               Request ‖ mac);  SignWithLabel(inviter, "TrommiInviteReveal", Reveal)
check code   = the first 36 bits of RefHash("Trommi Invite Code", Offer ‖ Request ‖ mac ‖ nonce), as six numbers
               0–63: indexes into the 64 emoji of app/web/core/check-emoji.ts
```

- 12.1.1 `role`: 1 human device, 2 agent device. `session_id`: zeros, or for an agent the session it shall take
  over. `hub` is a canonical address, at most 512 bytes: `https://` + lowercase host [+ `:port`], no path, no
  trailing slash; `http://` only for `localhost` and `127.0.0.1`; exactly
  `^(https://[a-z0-9]([a-z0-9-]*[a-z0-9])?(\.[a-z0-9]([a-z0-9-]*[a-z0-9])?)*|http://(localhost|127\.0\.0\.1))(:[1-9][0-9]{0,4})?$`.
  Anything else is refused, never normalised, in the link, the Request and the hub sign-in (12.3).
  In the link it is the base64url of its UTF-8, and `https://<app>` stands for the app's origin in the same
  canonical form; a link naming a version above 2 is `newer-version`, any other text `bad-format`, a link of
  four parts (without `expires_at`) included. `mac` and `offer_mac` are 32 bytes; `key_package` is at most 8192
  bytes. The three labels derived from the secret are used for nothing else; the deadline is part of their
  context, so a link whose deadline was changed names another invite and other keys.
- 12.1.2 Only a human device invites. It sets `expires_at` to its clock plus the invite life of the kind of
  device: 10 minutes for a human device, 15 minutes for an agent device (a new session or a takeover); the link
  and the Offer carry the same value. It computes `offer_mac` when it opens the invite and publishes it with the
  Offer (`POST /v1/invites`); the hub stores it and serves it with the Offer, and checks only its length (it
  never has the secret). An invite's Offer never changes: other terms, or opening again, mean a fresh secret and
  a fresh link. The new device, by its own clock, refuses a link (before it fetches anything, and again before it
  sends its Request) when the clock is more than 2 minutes past `expires_at` (`invite-expired`) or `expires_at`
  lies more than the invite life and 2 minutes ahead (`bad-invite`; before the Offer is fetched its kind is not
  known and the longer life, 15 minutes, applies). With a served Offer it does, before anything else and in
  this order: decodes it (`bad-format`); requires `room_id` and `invite_id` to be the link's; verifies
  `offer_mac` in constant time; verifies the signature by `inviter` (`bad-signature`); requires `expires_at` to
  be the link's and holds it to the clock as above. A missing, short or wrong `offer_mac`, a signature of
  another length than 64 bytes, and every mismatch are `bad-invite`; the new device then sends nothing, and the
  failure is local, not reported to the hub. Only then does it store its state and send the Request with the
  Offer's role and a fresh KeyPackage of its own (4.5). The MAC pins the Offer, and with it `inviter`, to the
  link: a hub cannot serve an Offer of its own under the invite id it knows. It gives no freshness: a genuine
  Offer can be served again while it has not expired, which the inviter's own state (used, burned, expired)
  answers. `offer_hash` and the check code take the Offer's bytes alone, without its signature and `offer_mac`.
- 12.1.3 The inviter accepts the first Request with a valid MAC that matches room, invite, hub, role and offer hash
  and is signed by the KeyPackage's key; marks the invite used; then publishes the Reveal. The new device checks the
  Reveal against invite, request hash and commitment. Both show the six emoji. A wrong MAC and every mismatch are
  `bad-invite`, a KeyPackage that fails 4.5 `bad-key-package`, a wrong signature `bad-signature`; a refused
  Request does not use the invite up. The new device is the signature key of that KeyPackage and nothing a hub or
  a caller says beside it; the hub checks a Request the same way, but for the MAC. Afterwards a
  Request meets `invite-used`, after `expires_at` by the inviter's clock (it set the deadline: no tolerance)
  `invite-expired`, after a burning `invite-burned`. The accepted Request posted again is answered with the same
  acceptance, also after `expires_at`: that accepts nothing new and does not move the 5 minutes to confirm.
- 12.1.4 Only after the human confirmed that they match does the inviter commit; the function that commits takes
  the confirmed code and request hash, recomputes them and refuses otherwise (`code-not-confirmed`). "They don't
  match" burns the invite. Expiry (`expires_at`), single use and the 5 minutes to confirm, which run from the
  accepted Request, are the inviter's to enforce.
- 12.1.5 **A human device:** the inviter commits the Add of that KeyPackage in the room group and sends the key
  handover (7.1); the new device accepts the Welcome only if it is for `room_id`, was committed by `inviter` and
  adds its own KeyPackage. The inviter then adds it to every live session group (5.2.7).
- 12.1.6 **An agent device:** the inviter commits the `agents` change in the room group, then founds the device's
  main session with that KeyPackage, or takes `session_id` over (5.3). The new device starts observing the room
  group (4.4) at the GroupInfo of `room_epoch`, whose GroupContext must hash to `room_state`, and accepts only if the `agents`
  Commit that names it was made by `inviter`.
- 12.1.7 The hub accepts an Add in the room group, or a key added to `agents`, only as the outcome of an invite: the
  KeyPackage or key of the Request the inviter revealed, the invited role, committed by the inviter (`bad-invite`).

## 13. The connector

- 13.1 **State** lives on disk outside the Claude session, one directory per connector installation, room and
  project folder (mode 0700, one process at a time by a file lock): the signature key, the OpenMLS storage of every
  group it is a leaf of, the private parts of its unused KeyPackages, its content keys, its chain state (9.0.1) and
  the hub cursor.
- 13.2 **Write order** (every client, not only the connector). One atomic write holds, together: the group state
  after a processed entry, the content key exported from it and the cursor. Whatever is sent is first written with
  the state it leaves behind: an envelope with its number, an MLS message with the ratchet state after it, a pending
  Commit; a retry sends the same bytes, and the hub answers a repeated post like the first. After `epoch-taken` the
  device fetches the accepted Commit: if it is its own, it merges, else it clears the pending one and builds again.
  An own Commit is merged at its place in the hub's order (5.4.1), when the device processes it from the log, also
  when the hub accepted the post: what the hub ordered before it opens only in the epoch it ends.
  An external commit is built on a copy of the storage that replaces the real one only when the hub accepted it. A
  KeyPackage's private part is written before the KeyPackage is uploaded. Nothing is acknowledged to Claude before
  its write.
- 13.3 **Restart on the same machine** needs no human: the connector loads its state, signs in, processes each
  group's log from its cursor in order, and is the same member.
- 13.4 **State behind, bad input, state lost.** Behind: process from the cursor. An entry from the hub that does
  not verify or process is not a lost state: the device keeps its last good state and cursor, shows `bad-group`
  and reports it (14.7). Only when its own directory is gone or does not load, or the hub no longer has the next
  entry (`gone`), is the installation a new device (4.3): it makes a new key and asks to be let in. A helper device
  is re-admitted by its opener (5.3.5), with no human. An agent device joins by link again and takes its session
  over (13.5).
- 13.5 **Another machine.** The human picks the Agent in the app and reconnects it there: the app makes a link for
  that session (12.1.1), the new connector joins with it, the human device takes the session over (5.3), which
  always removes the first machine's device, and hands the history over. The first machine's connector learns it
  from the Commit, wipes that session's state and stops.
- 13.6 The connector executes a human's answer, verdict or message only after the command gate (9.0.9).
- 13.7 An agent device holds one lease per room at the hub: `POST /v1/link` with a new random process id
  acquires it and gives a generation one above the last, valid 60 s; the same process renews it every 20 s with
  its generation, which stays; a renewal under an older generation fails and that process stops; every write carries it (`Trommi-Lease`), and an
  older generation is refused (`lease-lost`): of two processes on one state the later wins.

## 14. The hub

The hub is the MLS delivery service and the store. It holds no private key of a room.

- 14.1 It follows every group with `PublicGroup` and accepts a Commit only if: it parses and verifies there (framing,
  the committer's signature, proposals valid for the tree, the update path's public part); it builds on the current
  epoch and no other Commit took it; it obeys sections 3 to 5; the posted GroupInfo is signed by the committer, and
  its group context and tree hash equal the hub's own; a Welcome is present for every Add; the `SealedKey` of 8.2 is present.
  It cannot check membership or confirmation tags; members do.
- 14.2 It hands out each single-use KeyPackage once, the last-resort one when no other is left; it accepts a
  KeyPackage only from the device it names, verified.
- 14.3 It stores application messages of types it cannot read: it accepts them from a signed-in leaf of the group, in
  the current epoch, and keeps them 30 days (a sender marks a stroke piece `relay`, then it is never stored).
- 14.4 A removal ends the removed device's tokens and streams at once.
- 14.5 Content: 9.0.11. Invites: 12.1.7.
- 14.6 Every route is under `/v1/`.
- 14.7 **A Commit that members cannot merge.** The hub cannot check membership and confirmation tags or the
  encrypted path, so a holder of a stolen signature key (or a faulty client) can get such a Commit accepted. Nothing
  is ever withdrawn or rolled back. A leaf that cannot merge an accepted Commit keeps its state, shows `bad-group`
  and reports it (`POST /v1/groups/{group}/reject`); the hub tells the room's human devices which device made the
  Commit. If other leaves merged it, the reporting device comes back as a new device (4.3). If no human device can
  merge it: a session group is archived and the work continues in a new session; the room group is recovered with
  the code (8.7). Either way the person removes the device that made it.

**What the hub reads, per stored thing.**

| Stored | Readable | Not readable |
| --- | --- | --- |

| application messages | group, epoch, size, arrival time, the posting device | type, sender as signed, content |
| envelopes | sender, group, epoch, numbers and chain hashes, recipient, time, kind, timeline, object id, type, state, urgency, answered at, the hash of the version or request it refers to, register id, file ids, push flag, padded size | bodies: all text, titles, options, choices, register names and values, strokes |
| files, shares | id, exact size, uploader, object; share id, hash of the link secret, expiry | bytes, names, types, keys |

## 15. Push and Live Activity

- 15.1 For an accepted envelope with the push flag (9.2) the hub sends one push to every human device except the
  sender whose registration level allows it: `all`, or `knocking` (only urgency high or critical, and a lost agent).
- 15.2 A push carries no content. Web Push (RFC 8291): `{ room_id, change, urgency }`. APNs: a fixed text ("A new
  question." / "Urgent: a new question." / "An agent lost its connection.") and `nonce(12) ‖ AEAD.Seal(key, nonce, "trommi apns v1", { room_id, change,
  urgency, ticket })` under the 32 random bytes the app registered (D5). With `ticket` (the hub's own MAC over room,
  device, envelope and a 24-hour expiry) the notification extension fetches that one envelope and shows its title.
  Both JSON texts have one spelling, and a reader refuses any other: the fields in this order, no white space,
  `room_id` and `ticket` as base64url, `change` (at most 2^53 − 1) and `urgency` (0 to 3, as in section 9) as plain
  decimals. The ticket is at most 256 bytes and empty when there is no envelope to fetch; the sealed APNs payload
  is at most 512 bytes, its nonce random.
- 15.3 **Live Activity.** The hub counts `working` (agent devices whose link report says working) and `waiting`
  (open cards and permission requests). After a change, at most every 2 s, and every 10 minutes while one runs, it
  sends to Apple `{ aps: { timestamp, event, content-state: { working, waiting }, stale-date, relevance-score } }`:
  `start` when work begins and none runs (again only after it ended or 8 hours), `update` when a count changed,
  `end` when no agent works (dismissed after 15 minutes). Apple sees two counts and a random tag.

## 17. Known limits

- No forward secrecy for stored content, by decision: whoever holds a content key and the ciphertext reads that
  epoch; a human device holds all of them, the recovery code opens all of them.
- `recovery_mac` is held by every human device and outlives a removal: whoever copied a human device's state can,
  together with a hostile hub, forge sealed keys until the code is replaced (8.6).
- An update heals a copied group state. A copied device signature key is healed only by removing the device: until
  then its holder can publish KeyPackages and be added to new groups (as in any MLS deployment), and sign envelopes.
- Every leaf of a group reads all of that group's content of an epoch; only signatures separate senders. One content
  key serves all senders of an epoch with random 96-bit nonces: at the cap of 2^24 envelopes the chance of a repeat
  is below 2^-49.
- A chain shows a gap, a reordering or a second envelope under one number. A hub that withholds the newest envelopes
  of a sender, a whole group, or a removal from one device is noticed only when other evidence arrives (`heads`, a
  later envelope, a Commit); the order between different senders is the hub's and proves nothing.
- A Cut is the remover's view: envelopes of a removed device that the remover had not accepted are refused.
  A device holds one Cut per key and group, the one of the last removal: of a key that came back and was
  removed again, an envelope below that Cut is held to it by the chain alone (`prev`), not by the epoch rule.
- Whether an envelope is a void record is the hub's word where a device cannot check the reason again (9.0.8). The
  length of a sealed body is not signed (the signature covers its hash), so a pruned envelope does not show that it
  was `too-large`: a hub that serves such a record as stored makes every device count its header, in either form
  alike, and one that says `void` to some devices and not to others makes their object state differ. The device
  told `void` reports `hub-voided-other`; the others notice nothing.
- The hub sees who is in which group, when anyone writes, and every header field of section 14.
- Old work trails and live stroke pieces are not history: a device added later does not get them.
- Old content keys reach a device only in key handovers (7.1), which the hub keeps 30 days like every application
  message, and only from a device that holds them. A device that did not open its handover by then (it was away
  that long after it was added, or it took its Welcome late, after a room Commit had made the session stale or
  its first contact fail) reads the epochs before its own only once a human device hands them over again, on
  its request (`POST /v1/requests`, kind `handover`).
- Pruning (9.4) keeps no body for a case the hub cannot judge: a writer's earlier register value or Note version
  that a later Cut makes current again is already pruned, so devices that come later find that writer's value
  unreadable (9.3.4); a Note closed by arrival is pruned 30 days later with a concurrent open version that a
  higher lamport would keep (9.4.1); and a device that comes later sees only each writer's newest register value,
  so a value whose lamport jumped by more than the allowed step only across the pruned values is not taken by it
  (it would take some 16 million writes).
- A board snapshot written by a device that was not caught up for more than 30 days, and whose lamport is
  therefore below an older current snapshot, can let the hub prune items that older snapshot still needs (10.9);
  the web app writes a snapshot only while connected with nothing unsent.
- A Commit that verifies publicly but that members cannot merge costs a device its membership, a session its
  group, or the room a recovery (14.7); nothing detects it earlier than the members.
- A hub can serve a device that joins with the code an older, once valid state of the room; it cannot serve one of
  its own making (8.5). A `SealedKey` written by an opener alone is unauthenticated until a human device saw the
  group.
- What grows with the number of human devices N: a GroupInfo and a Welcome carry the whole tree (about 210
  bytes a leaf each), so every Commit of a group is posted with about 0.2 MB at N = 1000, and the founding of a
  session, which adds every human device in one request, has about 0.84 MB of the 1 MiB a Commit may have (1.1 MB
  as JSON, hence the JSON limit of 1.5 MiB): that request is what bounds N, near 1240. A device keeps the leaves and roles of every epoch of every group it
  holds (about 33 bytes a leaf and epoch, in the room group twice that), which is the product of N and the
  number of epochs: about 70 MB once 1000 devices have been added one by one, and 64 KB more with each further
  epoch of the room group. The own-leaf updates alone (5.2.9: each human device, each group, every 7 days) make
  about 52 N epochs a year in every group: at N = 100 some 17 MB a year and group on every device, at N = 1000
  some 1.7 GB, which no browser keeps: the limit of 1000 is what the requests and the rules carry, and a room
  near it needs these records kept as changes between epochs before it can live for years. A join costs one
  Commit in the room group and one in every live session (5.2.7), a removal the same (5.2.8); a recovery
  removes N − 1 leaves in every group and names a Cut for each (72 bytes).
- Expiry and freshness use the local clock of the device that enforces them; header times are claims.
- The check code has 36 bits; each attempt burns an invite. Whoever serves the client's code can use the keys.
- The Offer's MAC proves possession of the link's secret, not who the inviter is. Within a link's deadline,
  whoever holds the whole link, together with a hostile hub, can forge an Offer; only the comparison of the six
  emoji with the real inviter's screen protects against that. The deadline is judged by the joining device's own
  clock. The MAC does not show that what the hub serves is the newest.
- Not audited.

## 19. Vectors the core must produce

`spec/vectors/*.json`, one file per item below, made by `trommi-core` with a seeded random source, checked in
every binding.

1. Encodings: `TrommiRoom`, `TrommiSession`, `CommitNote`, `TrommiMessage` of each type.
2. A room played through, every message in bytes: founding; a session founded; a second human device added with its
   handover; its external commits into the session; an own-leaf update; removal of a human device with Cuts; an
   agent enrolled; a takeover with and without history; a helper founded by its opener; a helper device added and
   re-admitted; `content_key` for every group and epoch.
3. Commits that must be refused, each with its code: an agent committing in the room group; an opener removing a
   human leaf; a founding Commit missing a human device; a main session with two agent leaves; a returning key; a
   stale `room_epoch`; a second Commit for an epoch; a standalone proposal; a changed `TrommiSession`.
4. An observer following the room group from a GroupInfo.
5. Recovery: the keys from a code; a `SealedKey` and its opening; a join with the code; a recovery with Cuts and a
   new code with its `RecoveryLink`; a join with a wrong signature (`bad-signature`).
6. Envelopes: one of each kind, full and pruned, with header, padded body, hash and signature; the four binds; a
   chain of three; a void record; what checks 1 to 8 refuse, one case per code.
7. Files: an empty, a small and a two-chunk file; a wrong hash; a cut file. A Share link.
8. An invite for a human device and one for an agent device with every message, hash and the check code; what
   12.1.4 refuses. A hub sign-in.

9. The Scribble Board and the live messages: packed points; a board item of each content type; a history of
   items with the snapshot file it gives in any order of arrival; a work trail step and stroke pieces; what a
   reader of each refuses.
10. The account (`account.json`): the Emergency Kit of an account without an e-mail, whose keys are salted with
    the account id (8.8.2), beside `account-vectors.json` for an account with one.

**Conformance tests** the core and the hub must pass beside the vectors:

1. The whole of section 8 in one run: found, write in three groups over many epochs, lose every device, recover
   with the code against a hub that offers a room of its own making, an older state, a row without `mac`, a swapped
   row; then replace the code and recover again across the `RecoveryLink`.
2. A hostile hub: withholds a removal from one device, serves an old GroupInfo, drops the newest envelopes of one
   sender, reorders within a chain, serves a fork; each ends in the named finding.
3. Removal of a human device across 50 live sessions, with a crash after the room Commit and another device
   finishing; nothing is accepted from or for the removed device in between.
4. Catch-up of a device after 1 000 changes across 20 groups with devices coming and going, in the hub's order;
   the same log in another order is refused.
5. A crash between every two steps of 13.2 for an envelope, a Commit, an external commit and a command.
6. Two Commits racing for one epoch; a takeover racing with a helper founding; a founding with a missing
   KeyPackage; a Commit the members cannot merge (14.7).
